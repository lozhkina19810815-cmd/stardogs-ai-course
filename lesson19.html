Подключение источника данных:
коннектор iiko шаг за шагом

11 минут читать · 15 минут делать

Ваш агент уже общается через Telegram и читает файлы из Google. Теперь подключим к нему iiko — систему, где видна вся выручка, чеки и продажи по точкам. Сейчас, чтобы агент ответил «на сколько упала выручка в конкретной точке в марте», цифры нужно выгрузить из iiko и дать ему вручную — каждый раз чьё-то время. Этот урок — как подключить iiko напрямую, чтобы агент брал данные сам. 4 шага, делаете сами, без айтишника.

У iiko есть OLAP API (программный доступ к отчётам) — поэтому подключаем напрямую. Если у вашей системы такого доступа нет — остаётся ручной экспорт файлом; агент и так умеет работать с файлами.

Шаг 1. Доступ и ключи

Логин и пароль от iiko у вас уже есть — те самые, которыми вы заходите в iiko на своём компьютере. Документацию тоже не нужно изучать самому: её читает агент.

Как это сделать — скажите агенту:
«Вот адрес моего сервера iiko: [вставьте], мой логин и пароль: [вставьте]. Сохрани логин и пароль в файл .env, не в чат. Вот документация iiko — https://ru.iiko.help/articles/api-documentations/olap-otchety-v2 — разберись, как делать запрос за нужный период.»

Агент сохранит ключи в .env и разберёт документацию. Ключи в .env — правило для любой системы: файл живёт только на вашем компьютере, агент читает из него автоматически, в код и чат ключи не попадают.

Если упрётесь в блокировку — решайте системно, не костылём

Наш кейс. Агент работает через зарубежный VPN. iiko-сервер принимал подключения только с российских адресов, а VPN даёт зарубежный; плюс ТСПУ (технические фильтры на международных каналах) обрывали соединение. Первое «решение»: вручную выключать VPN перед каждой выгрузкой. Работало, но костыль — ручное действие каждый раз, легко забыть.

Поддержка iiko подтвердила: ТСПУ на маршруте до их дата-центра, повлиять не могут. Решили со стороны клиента: раздельный туннель (split tunnel) — трафик к адресам iiko идёт напрямую мимо VPN, остальной — через VPN. Настраивается один раз как фоновая служба. iiko видит российский адрес, VPN включён, выключать руками больше не нужно. Принцип: найти причину блокировки → закрыть класс проблем навсегда.
Как это сделать — скажите агенту:
«iiko не пускает, потому что я под зарубежным VPN. Настрой раздельный туннель: трафик только к адресам iiko пусть идёт напрямую мимо VPN, остальное как есть. И закрепи фоновой службой, чтобы пережило перезагрузку.»

Агент предложит решение и нужные команды и выполнит основную работу. Но настройка сети может потребовать вашего пароля от компьютера и пары попыток — это единственный шаг урока, где иногда нужна рука технического человека. Если упрётесь — не страшно: один раз настроили, дальше работает само.

Шаг 2. Скрипт-коннектор

Коннектор — небольшая программа-посредник: авторизуется в iiko по ключам из .env, отправляет запрос на нужный отчёт, возвращает данные агенту в читаемом виде. Агент пишет его сам по той документации, которую вы дали на шаге 1.

Как это сделать — скажите агенту:
«Напиши скрипт-коннектор к iiko: авторизуйся по логину/паролю из .env, отправь запрос на нужный отчёт, верни данные в читаемом виде.»

Ваша роль — дать команду и проверить результат. Код руками писать не нужно.

Шаг 3. Проверка — сверить с независимым эталоном

Коннектор работает — не доверяйте цифрам сразу. Один раз сверьте ключевую цифру с источником, который уже знаете как достоверный: старый ручной отчёт, выгрузка через интерфейс системы, расчёт коллеги.

Как это сделать — скажите агенту:
«Сверь одну ключевую цифру из выгрузки с моим ручным отчётом за тот же период. Совпало — продолжаем, разошлось — ищем где.»
Как проверяли у нас. Запросили данные за январь 2026 и сравнили с ручным эталонным отчётом коллеги-аналитика. Делили на каналы «зал» и «доставка» по типу оплаты — в iiko именно это поле надёжно их различает. Результат коннектора: зал около 78%, доставка около 22%. Ручной эталон — те же цифры, точь-в-точь. Совпадение — можно доверять.

Шаг 4. Задокументировать коннектор

Сразу после проверки — записать, пока контекст свежий. Агент читает этот файл сам при следующем запуске — не начинает с нуля. Файл в репозитории → едет с бэкапом агента, знание не теряется при смене версии.

Как это сделать — скажите агенту:
«Запиши файл проекта iiko с тремя разделами: Доступы (логин/пароль, как подключиться), Режимы (как работает, обход VPN), Отчёты (что можно строить из этих данных).»

Что агент теперь умеет

Из данных iiko агент строит любой отчёт за любой период. Раньше — часы ручной выгрузки, теперь — минуты запроса. Например: разбор конкретной точки (выручка, динамика по месяцам, продуктовый состав), ABC-анализ категорий, дашборд L4L (сравнение точек за сопоставимые периоды), срез зал/доставка — и любой другой под вашу задачу.

Всё это стало доступно в первые несколько минут после того, как коннектор прошёл проверку с эталоном.

4 камня

Камень 1. Ключи в коде или в чате

Ключ в коде рано или поздно уйдёт не туда. Ключ в чате агент упомянет в неожиданный момент. Только .env.

Камень 2. Костыль вместо системного решения

Если через ваш VPN система не подключается — выключать VPN руками перед каждой выгрузкой не решение, а костыль: ручное действие каждый раз, легко забыть. Скажите агенту разобраться с причиной и закрыть навсегда (у нас — раздельный туннель, настроен один раз).

Камень 3. Не проверить с эталоном — доверять цифрам вслепую

Правдоподобность не равна правильности. Один раз сверьте до начала работы — иначе через месяц выяснится, что все решения строились на ошибочном разрезе.

Камень 4. Не задокументировать — следующая версия начнёт с нуля

Документация сразу после проверки, пока контекст свежий. Потом «некогда» превращается в утерянное знание.

Практика — 4 шага на 15 минут

Делаете для своей системы прямо сейчас — каждый шаг это конкретная команда агенту.

ШАГ 1
Назвать систему и передать доступ агенту · 3 мин

Скажите агенту:

«Моя система с рабочими данными — [название: iiko / 1С / Bitrix24 / AmoCRM / другое]. Вот её адрес и мой логин/пароль: [вставьте]. Сохрани логин/пароль в .env. Найди документацию по API этой системы и разберись как делать запрос.»

Если API у системы нет — агент скажет об этом; данные пока передаёте файлом вручную.

ШАГ 2
Попросить написать коннектор · 4 мин
«Напиши скрипт-коннектор к [система]: авторизуйся по логину/паролю из .env, отправь запрос на выгрузку данных за последний месяц, верни в читаемом виде.»

Агент пишет скрипт — ваша задача проверить что он вернул данные.

ШАГ 3
Сверить с эталоном · 5 мин
«Сверь одну ключевую цифру из выгрузки с моим ручным отчётом за тот же период. Совпало — продолжаем, разошлось — ищем где.»

Подготовьте любой ручной отчёт за тот же период — выгрузку через интерфейс системы или прошлый расчёт.

ШАГ 4
Задокументировать и закрепить в CLAUDE.md · 3 мин
«Запиши файл проекта [система] с тремя разделами: Доступы, Режимы, Отчёты. Потом допиши в CLAUDE.md три правила из урока про коннекторы.»

Смотрите блок ниже — там готовый текст правил.

✅ Закрепить в CLAUDE.md

Три правила — применимы к любому коннектору, не только iiko. Скажите агенту:

«Я прошёл(ла) Урок 5 Блока 3 "Подключение источника данных". Допиши в CLAUDE.md три правила:
(1) Ключи доступа к любым внешним системам (API-ключи, логины, пароли) — только в файл .env. Никогда в код, никогда в чат.
(2) При препятствии с внешней системой — сначала найти причину, потом решать системно. Не предлагать костыль — ручное действие на каждый раз.
(3) После подключения нового источника данных — сверить хотя бы одну ключевую цифру с независимым эталоном до начала работы. Без эталона — не считается.»

Проверка: откройте CLAUDE.md, убедитесь что три правила добавлены.

Шпаргалка

  • Зачем. Агент мог работать с данными iiko и раньше — но только если их выгружали вручную. Коннектор убирает этот ручной труд: агент берёт данные сам по вашей команде.
  • Шаг 1 — доступ. Скажите агенту: «Логин/пароль iiko — [данные]. Сохрани в .env. Вот документация — разберись как делать запросы.» Ключи только в .env. Если не коннектится через VPN — скажите агенту настроить раздельный туннель.
  • Шаг 2 — коннектор. Скажите агенту: «Напиши скрипт-коннектор: авторизуйся из .env, запроси отчёт, верни данные.» Код пишет агент, не вы.
  • Шаг 3 — проверка. Скажите агенту: «Сверь ключевую цифру с моим ручным отчётом за тот же период.» У нас зал ~78% / доставка ~22% совпали с ручным эталоном точь-в-точь.
  • Шаг 4 — документация. Скажите агенту: «Запиши файл проекта: три раздела — доступы / режимы / отчёты.» Агент читает его сам при следующем запуске.
  • 4 камня: ключи не в .env / костыль вместо системного решения / цифры без эталонной сверки / нет документации.
  • Метрика успеха: агент выгружает данные из вашей системы сам, цифры сверены с эталоном, файл проекта записан, три правила в CLAUDE.md.
