Книга Крола
по Claude Code

Наша выжимка ключевых находок • Применимо к Стардогс

Алексей Крол — автор подхода «Теория каст и ролей». Его книга про Claude Code стала одним из источников нашей архитектуры. Здесь — ключевые находки, которые мы применяем или собираемся применять.

Топ-5 к внедрению

1CLAUDE.md — сократить до ядра

Крол пишет: ~200 строк, только ядро (миссия, ключевые ограничения, структура сессии). Не превращать в регламент — остальное через @import из модулей.

Для нас: ядро в CLAUDE.md, детали в rules/. Модульность через `@path` для разных зон проекта.

2Playbooks → нативные skills

Playbook = текст, который агент читает и интерпретирует. Skill = пакет, который Claude Code исполняет нативно, с принудительным чек-листом и CONTRACT.

Для нас: зрелые playbooks (ценообразование, отзывы, рутины) переводить в skills. Skill = исполняемое, playbook = справочное.

3Жёсткие запреты — в settings.json

CLAUDE.md — это рекомендация, её можно обойти в моменте. settings.json — архитектурный запрет, обойти нельзя.

Для нас: опасные операции (удаление файлов Ирины, перезапись таблиц) — в permissions deny. Не надеемся на дисциплину, делаем невозможным.

4Субагент-ревьюер

Исполнитель делает, ревьюер проверяет — это разные роли. Перед финализацией важного результата запускается отдельная проверка.

Для нас: для таблиц и отправок во внешние чаты — субагент-ревьюер перед финализацией. Снижает процент ошибок, видимых получателю.

5Hook на завершение сессии

Автопроверка при выходе: состояние обновлено? Handoff записан? Журнал заполнен? Не полагаемся на память.

Для нас: автоматический hook закрытия сессии, который блокирует выход без записанного контекста. Без этого — забывается раз в неделю.

Мелкие, но полезные приёмы

  • Техника интервью: при размытой задаче — 3–5 уточняющих вопросов, не додумывать. «Что должно получиться? Кто получатель? Есть ли эталон? Что точно НЕ нужно? Когда нужно?»
  • Diff-отчёт: после правок в таблицах обязательно «было X → стало Y». Без этого человек не понимает что изменилось.
  • Колонка iterations: в трекинге задач считаем сколько переделок до «готово». Метрика качества постановки задачи, а не усилий агента.
  • Path-scoped rules: разные правила для разных зон проекта (telegram-bot/ ≠ memory/ ≠ scripts/). Не грузить агенту всё сразу.
  • Шаблон делегирования: цель + границы + формат результата + правило эскалации. Без этого агент додумывает.
  • Разделение «разговор» vs «задача»: если нет 4 элементов (что / материал / ограничения / критерий готовности) — это разговор, переспросить.

Workflow: где мы не согласны с Кролом

Крол предлагает «голый чек-лист» — чистую последовательность шагов. Наша практика показала, что этого недостаточно.

Наш workflow = playbook (с контекстом и камнями) + принудительный чек-лист (skill/hook).

Чек-лист без объяснения «почему» приводит к повторению тех же ошибок. Playbook с описанием камней — это память, которую нельзя потерять.

Крол пишет для человека с памятью. Мы строим для агента без памяти. Это разный формат.

Общий вывод

По шкале зрелости Крола — мы на уровне 4–5 из 5. Пробелы не в архитектуре, а в использовании нативных механизмов Claude Code (skills, path-scoped rules, permissions deny) и в формализации ревью-фазы перед отправкой результата человеку.

То есть большая часть внедряемого не требует переписывания системы — это настройка существующих инструментов Claude Code, которые мы раньше обходили стороной.
